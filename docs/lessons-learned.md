# Lessons Learned — 프로세스 적용 교훈

**프로젝트명:** DevTrack  
**작성일:** 2026-06-02 (최종 정리)  
**작성자:** 최우식  

---

## 1. 요구사항 분석 단계

### 바이브코딩 적용 방식
- Claude와의 대화를 통해 초기 기능 목록을 브레인스토밍
- "개인 개발자가 쓰는 이슈 트래커에 꼭 필요한 기능이 뭐야?"라는 질문으로 시작
- AI가 제안한 기능 중 7일 내 구현 가능한 것만 선별 (MVP 범위 확정)

### 교훈
- **AI는 요구사항 도출을 빠르게 해주지만, 우선순위 결정은 사람이 해야 한다.** AI가 제안하는 기능은 이상적이지만 현실적 제약(시간, 인원)을 반영하지 못한다.
- 요구사항 명세서를 작성하고 나서야 "어디까지가 MVP인가"가 명확해졌다. 문서 작성 자체가 범위 정의 도구였다.

---

## 2. 시스템 설계 단계

### 바이브코딩 적용 방식
- 데이터 모델(Issue 인터페이스) 설계를 AI와 함께 논의
- "localStorage로 어떻게 저장하면 좋을까?" 질문으로 스키마 확정
- 컴포넌트 트리 구조를 AI에게 검토 요청

### 교훈
- **설계 문서를 먼저 작성하고 AI에게 코드를 요청하면 결과물 품질이 확연히 높아진다.** 설계 없이 "만들어줘"라고 하면 AI도 애매한 가정을 많이 한다.
- 와이어프레임(텍스트 기반이라도)을 그리면 AI가 컴포넌트를 더 정확하게 분리해준다.

---

## 3. 구현 단계

### 바이브코딩 적용 방식
- 컴포넌트 하나씩 AI에게 생성 요청 (한 번에 전체 요청 X)
- 생성된 코드를 직접 읽고 이해한 뒤, 프로젝트 컨텍스트에 맞게 수정
- 오류 발생 시 에러 메시지 전체를 AI에게 붙여넣어 디버깅

### 잘 된 점
- 반복적인 보일러플레이트 코드(폼, 모달, 배지 컴포넌트)를 AI가 빠르게 생성해 줌
- 구현 시간이 예상 대비 약 40% 단축

### 아쉬운 점
- AI가 생성한 코드가 프로젝트 기존 코드와 스타일이 달라 통일하는 데 시간 소요
- AI가 존재하지 않는 prop을 전달하는 실수를 종종 함 → 직접 타입 검토 필요

### 교훈
- **바이브코딩은 "AI가 다 만들어주는 것"이 아니라 "AI가 초안을 쓰고 사람이 완성하는 것"이다.**
- 컴포넌트를 작은 단위로 나눠서 요청할수록 AI의 결과물이 정확하다.

---

## 4. 테스트 단계

### 바이브코딩 적용 방식
- 테스트 케이스 목록 작성을 AI와 함께 진행
- 버그 발견 시 재현 방법을 AI에게 설명하고 수정 코드 제안 요청

### 교훈
- **AI는 테스트 케이스 설계를 잘 도와주지만, 실제 실행은 사람이 해야 한다.**
- 수동 테스트 체크리스트를 문서화해두니 빠뜨리는 케이스가 줄었다.

---

## 5. 품질 관리 단계

### 바이브코딩 적용 방식
- GitHub 커밋 히스토리로 작업 이력 관리
- 각 기능 완료 시 커밋하여 롤백 가능하게 유지
- AI에게 작성된 코드의 잠재적 문제점 리뷰 요청

### 교훈
- **형상 관리(Git)와 바이브코딩을 병행하면 AI가 만든 코드의 품질을 추적할 수 있다.**
- AI 생성 코드도 반드시 커밋 단위로 분리해야 나중에 문제 발생 시 원인 파악이 쉽다.

## 6. 종합 평가

| 항목 | 평가 |
|------|------|
| 개발 속도 향상 | ★★★★☆ — 반복 코드 작성 시간 대폭 감소 |
| 코드 품질 | ★★★☆☆ — AI 생성 코드는 반드시 검토 필요 |
| 요구사항 명확화 | ★★★★☆ — AI와의 대화가 요구사항 도출에 효과적 |
| 학습 효과 | ★★★★★ — AI 코드를 읽고 이해하면서 새로운 패턴 학습 |
| 프로세스 준수 | ★★★★☆ — 문서화가 번거롭지만 결과적으로 도움이 됨 |

### 최종 결론

> 바이브코딩은 프로세스가 없으면 "빠른 혼돈"이 되고, 프로세스가 있으면 "빠른 개발"이 된다.  
> AI 도구의 생산성은 요구사항 분석, 설계, 테스트, 형상 관리라는 전통적인 소프트웨어 공학 프로세스 위에서 극대화된다.
